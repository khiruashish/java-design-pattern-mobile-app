    Factory Method¶

    L1 🟢 Foundations · ⏱ 40 min read · Prerequisites: Singleton, SOLID Principles

    TL;DR

    Factory Method moves the decision "which class do I create?" out of the code that uses the object. In the classic form a base class calls an abstract create...() method that subclasses override. In everyday Java you'll more often see its relatives: static factory methods (List.of, Money.ofCents), parameterised factories (switch on a kind) and Supplier<T>. Use it when the concrete type varies; skip it when new is clear and stable.

    1. What It Is¶

    Plain English. Instead of writing new SmsReceipt() inside your checkout code, you ask a method to give you "a receipt". Which kind of receipt comes back is decided somewhere else: in a subclass, in a configuration lookup, or in a function you were handed. Your checkout code only knows the interface.

    Precise definition (GoF intent). "Define an interface for creating an object, but let subclasses decide which class to instantiate. Factory Method lets a class defer instantiation to subclasses." Roles:

    • Product: the interface the client uses (Receipt).
    • Concrete product: an implementation (SmsReceipt, EmailReceipt).
    • Creator: the class with the workflow, which calls the factory method (ReceiptSender).
    • Concrete creator: overrides the factory method to pick the product (SmsReceiptSender).

    The term is also used loosely for any method whose job is creating objects, including static factories. This page covers both, and says which is which.

    2. Why It Exists¶

    new couples the caller to one concrete class. When the class has to vary (by channel, by country, by environment, in tests), every new becomes an if chain, copied around the codebase. Adding a new variant then means editing every chain, which breaks the Open/Closed Principle. Factory Method puts creation in one overridable or replaceable place, so the workflow code stays closed for modification and the set of products stays open for extension.

    3. Mental Model / Analogy¶

    Analogy. A FreshCart store manager's checklist says "print the receipt" for every order. The manager doesn't decide how; each store's setup does. The kiosk store prints a paper slip, the online store sends an email. The checklist (workflow) is the same; the "make a receipt" step is filled in per store (factory method).

    Technical model. A factory method is a seam: one call site where the concrete type is chosen. Everything above it depends on an interface.

    4. How It Works¶

    classDiagram

        <<interface>>
        +render(orderId, totalInCents) String

    sequenceDiagram

    The base class's send is a template: fixed steps, with one step (creation) left to subclasses. That's why Factory Method is often described as a special case of Template Method.

    5. Subtopics¶

    Classic subclass-based Factory Method¶

    Description. The GoF form. An abstract creator class owns a workflow and declares an abstract (or default) createX() method. Each concrete creator subclass overrides it to return one concrete product.

    Advantages / features. Workflow written once; new products added by new subclasses without touching the workflow; the creator can't forget a step because send is final.

    ClassicFactoryMethodDemo.java
    import java.util.List;

/** Classic GoF Factory Method: the base class's algorithm calls an abstract creation method. */
public class ClassicFactoryMethodDemo {

    interface Receipt { String render(String orderId, long totalInCents); }

    record SmsReceipt() implements Receipt {
        public String render(String id, long cents) { return "FreshCart: order " + id + " paid " + money(cents); }
    }
    record EmailReceipt(String brandColour) implements Receipt {
        public String render(String id, long cents) { return "<h1 style='color:" + brandColour + "'>Order " + id + "</h1><p>Total " + money(cents) + "</p>"; }
    }

    /** Creator: owns the workflow, defers WHICH receipt to subclasses. */
    abstract static class ReceiptSender {
        protected abstract Receipt createReceipt();                                       // (1)!

        final String send(String orderId, long totalInCents) {                           // (2)!
            if (totalInCents <= 0) throw new IllegalArgumentException("total must be positive");
            Receipt receipt = createReceipt();
            return channel() + " -> " + receipt.render(orderId, totalInCents);
        }

        protected abstract String channel();
    }

    static final class SmsReceiptSender extends ReceiptSender {                          // (3)!
        protected Receipt createReceipt() { return new SmsReceipt(); }
        protected String channel() { return "sms"; }
    }

    static final class EmailReceiptSender extends ReceiptSender {
        protected Receipt createReceipt() { return new EmailReceipt("#2e7d32"); }
        protected String channel() { return "email"; }
    }

    static String money(long c) { return "$%d.%02d".formatted(c / 100, c % 100); }

    public static void main(String[] args) {
        for (ReceiptSender sender : List.of(new SmsReceiptSender(), new EmailReceiptSender())) {
            System.out.println(sender.send("FC-2101", 4_250));
        }
        try { new SmsReceiptSender().send("FC-2102", 0); } catch (IllegalArgumentException e) { System.out.println("rejected: " + e.getMessage()); }
    }
}
    1. The factory method: subclasses decide which Receipt to create.
    2. The workflow is final, so validation can't be skipped by a subclass.
    3. One concrete creator per product.

    Run it: java ClassicFactoryMethodDemo.java

    sms -> FreshCart: order FC-2101 paid $42.50
email -> <h1 style='color:#2e7d32'>Order FC-2101</h1><p>Total $42.50</p>
rejected: total must be positive
    Pros Cons
    Workflow is shared and protected One subclass per product: class explosion
    New products without editing the workflow (OCP) Inheritance couples creator and subclass
    Creation logic is in one obvious place Choosing which subclass still has to happen somewhere

    Use it in frameworks where users extend a base class anyway. Avoid it when the only thing a subclass would do is pick a type; pass a Supplier or use a parameterised factory instead. Real-world Java: java.util.AbstractList.iterator() and Collection.iterator() (each collection creates its own Iterator); Spring's AbstractApplicationContext has overridable create... methods such as createEnvironment(). Best practice: make the workflow method final and the factory method protected. Gotcha: don't call an overridable factory method from the creator's constructor: the subclass's fields aren't initialised yet.

    Parameterised factory method¶

    Description. One method takes a parameter (an enum, a string, a config value) and returns the matching product. With Java 21's sealed interfaces and switch expressions, the compiler checks that every kind is handled.

    Advantages / features. One place to look; exhaustive switch; validation of input at the boundary; no subclass per product.

    ParameterisedFactoryDemo.java
    import java.util.Locale;

/** Parameterised factory method: one method, a parameter decides the product. */
public class ParameterisedFactoryDemo {

    sealed interface DeliveryOption permits Standard, Express, Scheduled {
        long feeInCents();
        String describe();
    }
    record Standard() implements DeliveryOption {
        public long feeInCents() { return 499; }
        public String describe() { return "standard (same day)"; }
    }
    record Express(int minutes) implements DeliveryOption {
        public long feeInCents() { return 799; }
        public String describe() { return "express in " + minutes + " min"; }
    }
    record Scheduled(String slot) implements DeliveryOption {
        public long feeInCents() { return 299; }
        public String describe() { return "scheduled " + slot; }
    }

    enum Kind { STANDARD, EXPRESS, SCHEDULED }

    /** The factory method. Callers never write `new Express(...)` themselves. */
    static DeliveryOption create(Kind kind, String slot) {                             // (1)!
        return switch (kind) {                                                          // (2)!
            case STANDARD -> new Standard();
            case EXPRESS -> new Express(30);
            case SCHEDULED -> {
                if (slot == null || !slot.matches("\\d{2}:\\d{2}-\\d{2}:\\d{2}")) throw new IllegalArgumentException("scheduled delivery needs a slot like 18:00-19:00");
                yield new Scheduled(slot);
            }
        };
    }

    /** Parsing user input is the factory's job too, with a helpful error. */
    static DeliveryOption fromRequest(String kind, String slot) {                       // (3)!
        try {
            return create(Kind.valueOf(kind.trim().toUpperCase(Locale.ROOT)), slot);
        } catch (IllegalArgumentException e) {
            if (e.getMessage().startsWith("No enum constant")) throw new IllegalArgumentException("unknown delivery kind '" + kind + "', use one of " + java.util.Arrays.toString(Kind.values()));
            throw e;
        }
    }

    public static void main(String[] args) {
        for (String[] req : new String[][] {{"standard", null}, {"Express", null}, {"scheduled", "18:00-19:00"}, {"drone", null}, {"scheduled", "evening"}}) {
            try {
                DeliveryOption o = fromRequest(req[0], req[1]);
                System.out.println(req[0] + " -> " + o.describe() + ", fee " + o.feeInCents());
            } catch (IllegalArgumentException e) {
                System.out.println(req[0] + " -> rejected: " + e.getMessage());
            }
        }
    }
}
    1. The factory takes the kind as a parameter.
    2. A switch expression over an enum is exhaustive: adding Kind.DRONE without a case won't compile.
    3. A separate method parses untrusted strings and gives helpful errors.

    Run it: java ParameterisedFactoryDemo.java

    standard -> standard (same day), fee 499
Express -> express in 30 min, fee 799
scheduled -> scheduled 18:00-19:00, fee 299
drone -> rejected: unknown delivery kind 'drone', use one of [STANDARD, EXPRESS, SCHEDULED]
scheduled -> rejected: scheduled delivery needs a slot like 18:00-19:00
    Pros Cons
    All creation rules in one method The method changes for every new kind (not strictly OCP)
    Compiler-checked exhaustiveness with sealed types/enums Can grow into a giant switch
    Easy validation and error messages Kinds must be known at compile time

    Use it when the set of products is small, known and owned by your team. Avoid it when third parties add products (use a registry or ServiceLoader). Real-world Java: java.nio.charset.Charset.forName("UTF-8"), java.time.ZoneId.of("Asia/Kolkata"), JDBC DriverManager.getConnection(url). Best practice: parse strings into an enum first, then switch on the enum. Gotcha: a default -> branch on an enum switch disables the exhaustiveness check; leave it out.

    Static factory methods (Effective Java, Item 1)¶

    Description. A static method that returns an instance, used instead of (or alongside) a public constructor: Money.ofCents(250), List.of(1, 2). Not the GoF pattern strictly, but the most common "factory" in Java code.

    Advantages / features (Bloch's list). Methods have names (ofCents vs parse); they can return a cached instance; they can return a subtype; the returned class can vary between calls and releases; they can validate before construction.

    StaticFactoryDemo.java
    import java.math.BigDecimal;
import java.math.RoundingMode;
import java.util.concurrent.ConcurrentHashMap;
import java.util.Map;

/** Static factory methods (Effective Java, Item 1): names, caching, validation, subtype freedom. */
public class StaticFactoryDemo {

    static final class Money {
        private static final Map<Long, Money> SMALL = new ConcurrentHashMap<>();
        private final long cents;

        private Money(long cents) { this.cents = cents; }                                // (1)!

        static Money ofCents(long cents) {                                               // (2)!
            if (cents < 0) throw new IllegalArgumentException("money cannot be negative: " + cents);
            return cents <= 1_000 ? SMALL.computeIfAbsent(cents, Money::new) : new Money(cents);   // (3)!
        }

        static Money parse(String text) {                                               // (4)!
            BigDecimal amount = new BigDecimal(text.replace("$", "").trim());
            if (amount.scale() > 2) throw new IllegalArgumentException("too many decimals: " + text);
            return ofCents(amount.setScale(2, RoundingMode.UNNECESSARY).movePointRight(2).longValueExact());
        }

        static Money zero() { return ofCents(0); }

        @Override public String toString() { return "$%d.%02d".formatted(cents / 100, cents % 100); }
    }

    public static void main(String[] args) {
        System.out.println(Money.parse("$12.99") + " " + Money.ofCents(250) + " " + Money.zero());
        System.out.println("small amounts cached: " + (Money.ofCents(99) == Money.ofCents(99)));
        System.out.println("large amounts not cached: " + (Money.ofCents(50_000) == Money.ofCents(50_000)));
        for (String bad : new String[] {"$1.999", "-5"}) {
            try { Money.parse(bad); } catch (IllegalArgumentException e) { System.out.println("rejected: " + e.getMessage()); }
        }
        System.out.println("JDK examples: " + Integer.valueOf(127).equals(Integer.valueOf(127)) + ", " + java.util.List.of(1, 2) + ", " + java.time.LocalDate.of(2026, 11, 2));
    }
}
    1. Private constructor: the static factories are the only way in.
    2. A named factory says what the number means: cents, not rupees.
    3. Small, frequent values are cached and shared (safe because Money is immutable).
    4. A second factory with a different name for a different input.

    Run it: java StaticFactoryDemo.java

    $12.99 $2.50 $0.00
small amounts cached: true
large amounts not cached: false
rejected: too many decimals: $1.999
rejected: money cannot be negative: -500
JDK examples: true, [1, 2], 2026-11-02
    Pros Cons
    Descriptive names Harder to find in Javadoc than constructors
    Caching and instance control Classes without public/protected constructors can't be subclassed
    Can return subtypes or hide implementation classes Identity (==) behaviour may surprise readers
    Validation in one place Too many factory names confuse callers

    Use it for value types, immutable objects and APIs that may change implementation. Avoid it when a plain constructor is perfectly clear and you need subclassing. Real-world Java: List.of, Optional.of, Integer.valueOf (caches -128..127), LocalDate.of, Path.of, EnumSet.of (returns RegularEnumSet or JumboEnumSet by size). Best practice: follow the JDK naming conventions: of, from, valueOf, parse, getInstance, newInstance, create. Gotcha: never compare cached objects with == in business code; Integer.valueOf(1000) == Integer.valueOf(1000) is false.

    Simple factory vs. Factory Method¶

    Description. A simple factory is a class with a creation method that decides the type (often from a parameter); it isn't one of the GoF patterns. Factory Method uses inheritance: the workflow class leaves creation to its subclasses. People mix the names up constantly, so it's worth seeing them side by side.

    Advantages of knowing the difference. You can pick the lighter tool (a simple factory is often enough), and you can talk about designs precisely in reviews and interviews.

    SimpleFactoryVsFactoryMethodDemo.java
    import java.util.Map;
import java.util.function.Supplier;

/** Simple factory (one class decides) vs Factory Method (subclasses decide). */
public class SimpleFactoryVsFactoryMethodDemo {

    interface Courier { String book(String orderId); }
    record InHouseCourier() implements Courier { public String book(String id) { return "in-house rider for " + id; } }
    record PartnerCourier(String partner) implements Courier { public String book(String id) { return partner + " courier for " + id; } }

    // ===================== Simple factory: a plain class with a creation method =====================
    static final class CourierFactory {                                                  // (1)!
        private final Map<String, Supplier<Courier>> byCity = Map.of(
                "pune", InHouseCourier::new,
                "mumbai", () -> new PartnerCourier("QuickDrop"),
                "delhi", () -> new PartnerCourier("ParcelGo"));

        Courier forCity(String city) {
            Supplier<Courier> s = byCity.get(city);
            if (s == null) throw new IllegalArgumentException("no courier configured for " + city);
            return s.get();
        }
    }

    // ===================== Factory Method: the workflow class leaves creation to subclasses =====================
    abstract static class Dispatcher {                                                   // (2)!
        abstract Courier courier();
        final String dispatch(String orderId) { return "[" + getClass().getSimpleName() + "] " + courier().book(orderId); }
    }
    static final class DarkStoreDispatcher extends Dispatcher { Courier courier() { return new InHouseCourier(); } }
    static final class MarketplaceDispatcher extends Dispatcher { Courier courier() { return new PartnerCourier("ParcelGo"); } }

    public static void main(String[] args) {
        CourierFactory factory = new CourierFactory();
        System.out.println("simple factory: " + factory.forCity("mumbai").book("FC-1"));
        try { factory.forCity("goa"); } catch (IllegalArgumentException e) { System.out.println("simple factory: rejected: " + e.getMessage()); }
        System.out.println("factory method: " + new DarkStoreDispatcher().dispatch("FC-2"));
        System.out.println("factory method: " + new MarketplaceDispatcher().dispatch("FC-3"));
    }
}
    1. Simple factory: one object decides, here from a table keyed by city.
    2. Factory Method: the workflow class declares courier() and subclasses decide.

    Run it: java SimpleFactoryVsFactoryMethodDemo.java

    simple factory: QuickDrop courier for FC-1
simple factory: rejected: no courier configured for goa
factory method: [DarkStoreDispatcher] in-house rider for FC-2
factory method: [MarketplaceDispatcher] ParcelGo courier for FC-3
    Simple factory Factory Method
    Mechanism A method decides (data, switch) Subclasses override a creation method
    Who varies The input The creator subclass
    Workflow included No, it only creates Yes, creation is one step of it
    Adding a product Edit the factory (or its table) Add a subclass
    Best for Choosing by config or request data Frameworks with extensible base classes

    Use a simple factory when the choice depends on runtime data. Use Factory Method when different subclasses of a workflow need different products. Real-world Java: Calendar.getInstance(locale) is a simple (static) factory; AbstractList.iterator() is a factory method. Best practice: start with a simple factory; introduce subclasses only when the workflow itself differs. Gotcha: a simple factory with dozens of ifs is a smell; move to a registry (Map<String, Supplier<T>>).

    Supplier<T> as a factory¶

    Description. java.util.function.Supplier<T> is a one-method interface: T get(). Passing a Supplier is Factory Method without the subclass: the caller hands in "how to make one". Constructor references (ArrayList::new) are suppliers.

    Advantages / features. No inheritance; easy to swap in tests (deterministic IDs); composes with lambdas, maps and DI.

    SupplierFactoryDemo.java
    import java.util.ArrayList;
import java.util.List;
import java.util.UUID;
import java.util.function.Supplier;

/** Supplier<T> as a factory: pass "how to make one" into code that needs fresh objects. */
public class SupplierFactoryDemo {

    record PickList(String id, List<String> items) { }

    static final class Picker {
        private final Supplier<String> idFactory;                                        // (1)!
        Picker(Supplier<String> idFactory) { this.idFactory = idFactory; }

        List<PickList> split(List<String> items, int perList) {
            if (perList <= 0) throw new IllegalArgumentException("perList must be positive");
            List<PickList> lists = new ArrayList<>();
            for (int i = 0; i < items.size(); i += perList) {
                lists.add(new PickList(idFactory.get(), List.copyOf(items.subList(i, Math.min(i + perList, items.size())))));  // (2)!
            }
            return lists;
        }
    }

    public static void main(String[] args) {
        List<String> items = List.of("MILK", "BREAD", "EGGS", "RICE", "OIL");

        int[] seq = {0};
        Picker testPicker = new Picker(() -> "PL-" + (++seq[0]));                         // (3)!
        testPicker.split(items, 2).forEach(System.out::println);

        Picker prodPicker = new Picker(() -> "PL-" + UUID.randomUUID());                  // (4)!
        System.out.println("production ids look like PL-<uuid>: " + prodPicker.split(items, 5).get(0).id().matches("PL-[0-9a-f-]{36}"));

        Supplier<List<String>> freshList = ArrayList::new;                                // (5)!
        System.out.println("constructor reference gives a new object each time: " + (freshList.get() != freshList.get()));
    }
}
    1. The class depends on "something that makes IDs", not on UUID.
    2. A new ID per pick list, from whatever factory was injected.
    3. Tests get predictable IDs.
    4. Production gets random UUIDs, with no code change in Picker.
    5. A constructor reference is a factory: every get() creates a new list.

    Run it: java SupplierFactoryDemo.java

    PickList[id=PL-1, items=[MILK, BREAD]]
PickList[id=PL-2, items=[EGGS, RICE]]
PickList[id=PL-3, items=[OIL]]
production ids look like PL-<uuid>: true
constructor reference gives a new object each time: true
    Pros Cons
    No subclass needed No place for extra methods or a name for the factory
    Trivial to fake in tests Can't take arguments (use Function<A, T> then)
    Works with constructor references and maps Checked exceptions don't fit get()

    Use it when the only variation is "how to create one". Avoid it when creation needs several parameters or named operations; define a small factory interface instead. Real-world Java: ThreadLocal.withInitial(Supplier), Collectors.toCollection(TreeSet::new), Map.computeIfAbsent(key, Function), Optional.orElseGet(Supplier). Best practice: inject Suppliers for IDs, clocks-of-the-day and fresh buffers. Gotcha: a Supplier that returns the same object each time isn't a factory; document which one you expect.

    6. Examples (exactly 3, progressively harder)¶

    Example 1: Minimal (L1)¶

    Scenario: FreshCart sends order updates by SMS or push, chosen by a string from the customer's preferences.

    NotifierFactoryDemo.java
    /** Minimal Factory Method: callers ask for "a notifier for this channel" and never call `new` themselves. */
public class NotifierFactoryDemo {

    interface Notifier { String send(String to, String text); }

    record Sms() implements Notifier { public String send(String to, String t) { return "SMS " + to + ": " + t; } }
    record Push() implements Notifier { public String send(String to, String t) { return "PUSH " + to + ": " + t; } }

    static Notifier notifierFor(String channel) {                                       // (1)!
        return switch (channel) {
            case "sms" -> new Sms();
            case "push" -> new Push();
            default -> throw new IllegalArgumentException("unknown channel " + channel);
        };
    }

    public static void main(String[] args) {
        System.out.println(notifierFor("sms").send("+919876543210", "Your order is packed"));
        System.out.println(notifierFor("push").send("asha-phone", "Rider is 5 min away"));
        try { notifierFor("fax"); } catch (IllegalArgumentException e) { System.out.println("rejected: " + e.getMessage()); }
    }
}
    1. The only place that knows about concrete notifier classes.

    Run it: java NotifierFactoryDemo.java

    Output:

    SMS +919876543210: Your order is packed
PUSH asha-phone: Rider is 5 min away
rejected: unknown channel fax

    What to notice:

    • Callers only see Notifier; adding WhatsApp means one new class and one new case.
    • An unknown channel fails with a clear message instead of a NullPointerException later.

    Example 2: Realistic (in FreshCart grocery delivery)¶

    Scenario: Store managers download daily sales reports. The file extension decides the format, and new formats will be added.

    ReportExporterDemo.java
    import java.util.List;
import java.util.Locale;
import java.util.Map;
import java.util.function.Supplier;
import java.util.stream.Collectors;

/** FreshCart store managers export daily sales; the file name decides which exporter is created. */
public class ReportExporterDemo {

    record Sale(String sku, int quantity, long revenueInCents) { }

    interface Exporter {
        String contentType();
        String export(List<Sale> sales);
    }

    static final class CsvExporter implements Exporter {
        public String contentType() { return "text/csv"; }
        public String export(List<Sale> sales) {
            return "sku,quantity,revenue_cents\n" + sales.stream()
                    .map(s -> s.sku() + "," + s.quantity() + "," + s.revenueInCents()).collect(Collectors.joining("\n"));
        }
    }

    static final class JsonExporter implements Exporter {
        public String contentType() { return "application/json"; }
        public String export(List<Sale> sales) {
            return sales.stream().map(s -> "{\"sku\":\"" + s.sku() + "\",\"quantity\":" + s.quantity() + ",\"revenueCents\":" + s.revenueInCents() + "}")
                    .collect(Collectors.joining(",", "[", "]"));
        }
    }

    static final class ExporterFactory {
        private static final Map<String, Supplier<Exporter>> BY_EXTENSION = Map.of(       // (1)!
                "csv", CsvExporter::new,
                "json", JsonExporter::new);

        static Exporter forFileName(String fileName) {                                  // (2)!
            int dot = fileName.lastIndexOf('.');
            String ext = dot < 0 ? "" : fileName.substring(dot + 1).toLowerCase(Locale.ROOT);
            Supplier<Exporter> supplier = BY_EXTENSION.get(ext);
            if (supplier == null) throw new IllegalArgumentException("can't export '" + fileName + "', supported: " + BY_EXTENSION.keySet().stream().sorted().toList());
            return supplier.get();
        }
    }

    public static void main(String[] args) {
        List<Sale> sales = List.of(new Sale("MILK-1L", 42, 5_418), new Sale("BREAD-WHT", 17, 4_233));
        for (String file : List.of("pune-01-2026-11-02.csv", "pune-01-2026-11-02.JSON", "pune-01-2026-11-02.xlsx")) {
            try {
                Exporter exporter = ExporterFactory.forFileName(file);                   // (3)!
                System.out.println(file + " (" + exporter.contentType() + ")\n" + exporter.export(sales));
            } catch (IllegalArgumentException e) {
                System.out.println("rejected: " + e.getMessage());
            }
        }
    }
}
    1. A registry: extension to factory. Adding Excel later means adding one entry.
    2. The factory method: picks the exporter from the file name, case-insensitively.
    3. The report code never names a concrete exporter.

    Run it: java ReportExporterDemo.java

    Output:

    pune-01-2026-11-02.csv (text/csv)
sku,quantity,revenue_cents
MILK-1L,42,5418
BREAD-WHT,17,4233
pune-01-2026-11-02.JSON (application/json)
[{"sku":"MILK-1L","quantity":42,"revenueCents":5418},{"sku":"BREAD-WHT","quantity":17,"revenueCents":4233}]
rejected: can't export 'pune-01-2026-11-02.xlsx', supported: [csv, json]

    What to notice:

    • .JSON works because the extension is normalised.
    • The error lists the supported formats, which saves a support ticket.
    • Each call gets a fresh exporter, so exporters can keep per-file state safely.

    Example 3: Production-grade¶

    Scenario: Every FreshCart store (merchant) has a payment gateway: a card network, UPI, or a sandbox for testing. The type, endpoint and timeout come from configuration. Production must never use the sandbox, development must never hit a live card network, misconfiguration must fail clearly, and each merchant's client (with its connection pool) must be created only once.

    PaymentGatewayFactoryDemo.java
    import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicInteger;

/**
 * Production shape: a factory that builds payment-gateway clients from configuration.
 * - validates config and fails fast with a clear message
 * - refuses live gateways outside production and sandbox gateways in production
 * - caches one client per merchant (clients are expensive: TLS, connection pools)
 */
public class PaymentGatewayFactoryDemo {

    interface PaymentGateway { String charge(String orderId, long cents); }

    record SandboxGateway(String merchantId) implements PaymentGateway {
        public String charge(String orderId, long cents) { return "SANDBOX ok " + orderId + " " + cents + " (" + merchantId + ")"; }
    }

    record CardNetworkGateway(String merchantId, String endpoint, int timeoutMs) implements PaymentGateway {
        public String charge(String orderId, long cents) { return "LIVE ok " + orderId + " " + cents + " via " + endpoint + " timeout=" + timeoutMs + "ms"; }
    }

    record UpiGateway(String merchantId, String vpa) implements PaymentGateway {
        public String charge(String orderId, long cents) { return "UPI collect " + orderId + " " + cents + " to " + vpa; }
    }

    static final class GatewayFactory {
        private final String environment;
        private final Map<String, String> config;
        private final Map<String, PaymentGateway> cache = new ConcurrentHashMap<>();
        final AtomicInteger created = new AtomicInteger();

        GatewayFactory(String environment, Map<String, String> config) {
            this.environment = environment;
            this.config = Map.copyOf(config);
        }

        /** The factory method. Same merchant -> same client instance. */
        PaymentGateway forMerchant(String merchantId) {
            return cache.computeIfAbsent(merchantId, this::create);                       // (1)!
        }

        private PaymentGateway create(String merchantId) {
            String type = required(merchantId, "type");
            boolean prod = environment.equals("prod");
            PaymentGateway gateway = switch (type) {
                case "sandbox" -> {
                    if (prod) throw new IllegalStateException(merchantId + ": sandbox gateway is not allowed in prod");   // (2)!
                    yield new SandboxGateway(merchantId);
                }
                case "card" -> {
                    if (!prod) throw new IllegalStateException(merchantId + ": live card gateway is only allowed in prod");
                    int timeout = Integer.parseInt(config.getOrDefault(merchantId + ".timeoutMs", "3000"));
                    if (timeout < 100 || timeout > 30_000) throw new IllegalArgumentException(merchantId + ": timeoutMs must be 100..30000");
                    yield new CardNetworkGateway(merchantId, required(merchantId, "endpoint"), timeout);
                }
                case "upi" -> new UpiGateway(merchantId, required(merchantId, "vpa"));
                default -> throw new IllegalArgumentException(merchantId + ": unknown gateway type '" + type + "'");
            };
            created.incrementAndGet();
            return gateway;
        }

        private String required(String merchantId, String key) {                        // (3)!
            String value = config.get(merchantId + "." + key);
            if (value == null || value.isBlank()) throw new IllegalArgumentException(merchantId + ": missing config '" + merchantId + "." + key + "'");
            return value;
        }
    }

    public static void main(String[] args) {
        Map<String, String> config = Map.of(
                "pune-01.type", "card", "pune-01.endpoint", "https://cards.example/v2", "pune-01.timeoutMs", "2500",
                "pune-02.type", "upi", "pune-02.vpa", "freshcart.pune@bank",
                "dev-01.type", "sandbox",
                "bad-01.type", "card");

        GatewayFactory prod = new GatewayFactory("prod", config);
        System.out.println(prod.forMerchant("pune-01").charge("FC-3001", 4_250));
        System.out.println(prod.forMerchant("pune-02").charge("FC-3002", 1_999));
        System.out.println("cached: " + (prod.forMerchant("pune-01") == prod.forMerchant("pune-01")) + ", clients created: " + prod.created.get());

        for (String merchant : new String[] {"dev-01", "bad-01", "nope-99"}) {
            try { prod.forMerchant(merchant); } catch (RuntimeException e) { System.out.println("rejected: " + e.getMessage()); }
        }
        System.out.println(new GatewayFactory("staging", config).forMerchant("dev-01").charge("FC-T1", 100));
    }
}
    1. One client per merchant: computeIfAbsent creates it at most once, even under concurrency.
    2. Environment rules are enforced at creation, so a wrong config can't take a real payment in dev or a fake one in prod.
    3. Missing config fails with the exact key to fix.

    Run it: java PaymentGatewayFactoryDemo.java

    Output:

    LIVE ok FC-3001 4250 via https://cards.example/v2 timeout=2500ms
UPI collect FC-3002 1999 to freshcart.pune@bank
cached: true, clients created: 2
rejected: dev-01: sandbox gateway is not allowed in prod
rejected: bad-01: missing config 'bad-01.endpoint'
rejected: nope-99: missing config 'nope-99.type'
SANDBOX ok FC-T1 100 (dev-01)

    What to notice:

    • The checkout code calls forMerchant(id).charge(...) and never sees a concrete gateway class.
    • Two merchants, two clients created; repeated calls reuse them.
    • Every misconfiguration produces a message an on-call engineer can act on.

    7. Pros, Cons & Trade-offs¶

    Aspect Pros Cons
    Simplicity Callers depend on one interface Extra classes or indirection to read through
    Extensibility New products without changing callers (OCP) Classic form needs a subclass per product
    Performance Factories can cache, pool and reuse Negligible call overhead; caching adds memory
    Operability One place to validate config and log creation Creation failures surface at first use, not at startup, unless you warm up
    Testability Swap the factory or Supplier for fakes Hidden static factories are hard to replace
    Learning curve Familiar from the JDK (List.of) Name confusion: simple factory vs Factory Method vs Abstract Factory

    8. When to Use / When NOT to Use¶

    Use it when:

    • the concrete class depends on runtime data (country, channel, config, file type);
    • you want to hide implementation classes or cache instances;
    • a framework's base class needs subclasses to supply a part.

    Don't use it when:

    • there's one implementation and no realistic second one: new is fine (YAGNI);
    • a DI container already selects the implementation (Spring @ConditionalOnProperty, qualifiers);
    • you need families of related products that must match: use Abstract Factory;
    • the object has many optional parameters: use Builder.

    9. Best Practices¶

    1. Return interfaces, not concrete classes. (Consensus.)
    2. Prefer a static factory or Supplier before a creator class hierarchy. (Consensus in modern Java.)
    3. Validate inputs and configuration in the factory and fail with the key or value to fix. (Consensus.)
    4. Switch on an enum or sealed type without default, so the compiler finds missing cases. (Consensus.)
    5. Use a registry map when the number of products grows past a handful. (Opinion.)
    6. Name factories with JDK conventions (of, from, parse, create, forX). (Consensus.)
    7. Warm up critical factories at startup (create production clients eagerly) so config errors stop the deployment, not the first customer. (Opinion.)

    10. Pitfalls & Anti-Patterns¶

    The god factory

    Symptom: one ObjectFactory.create(String type) with 80 cases, used across the codebase. Root cause: every creation decision was centralised regardless of domain. Fix: one small factory per product family, owned by the module that owns the product.

    Sandbox in production (production failure mode)

    Symptom: orders marked paid but no money collected for two hours. Root cause: a config typo selected the sandbox gateway in production, and nothing checked the environment. Fix: enforce environment rules inside the factory (Example 3) and alert on the gateway type at startup.

    Overridable method called from a constructor

    Symptom: NullPointerException inside a subclass's createX() during construction. Root cause: the base constructor called the factory method before the subclass's fields were set. Fix: call factory methods lazily from the workflow, not from the constructor.

    Factory that hides new for no reason

    Symptom: UserFactory.createUser(name) that just does return new User(name), with one implementation forever. Root cause: pattern applied by habit. Fix: delete it and use the constructor or a record.

    12. Security Considerations¶

    • Never build class names from user input and load them with reflection (Class.forName(userInput)); map allowed values to factories explicitly.
    • Validate configuration that selects security-relevant implementations (payment, crypto, auth providers) and fail closed.
    • Don't log full configuration in factory errors; name the missing key, not the secret value.

    13. Performance & Scalability¶

    A factory method call costs the same as any method call, and the JIT inlines small ones. The performance wins come from what factories enable: caching immutable values (Integer.valueOf), reusing expensive clients per key (Example 3), and avoiding work for unused variants. Watch computeIfAbsent with slow creation: it holds a lock on that map bin while creating, so keep creation fast or create outside and use putIfAbsent.

    Test the factory's decisions directly, including the rejections:

import static org.junit.jupiter.api.Assertions.assertInstanceOf;

class PaymentGatewayFactoryTest {

    private final Map<String, String> config = Map.of(
            "m1.type", "card", "m1.endpoint", "https://cards.example/v2",
            "m2.type", "sandbox",
            "m3.type", "card", "m3.endpoint", "https://cards.example/v2", "m3.timeoutMs", "50");

    @Test

        var factory = new PaymentGatewayFactoryDemo.GatewayFactory("prod", config);

    Code that uses a factory should accept it (or a Supplier) through its constructor, so its tests can hand in fakes.

    15. Observability & Operations¶

    Log once per created client, with the type and non-secret settings (pune-01: card, timeout 2500ms). Export a gauge of clients created per type and a counter of creation failures. After a deployment, a jump in creation failures is a fast signal of bad configuration.

    17. Expert Deep Dive¶

    • The real decision is where the choice lives. In a subclass (classic), in data (registry, config), in the caller (Supplier), or in the container (DI). Seniors pick based on who adds new products: your team (enum switch), other teams (registry), third parties (ServiceLoader or plugins).
    • ServiceLoader is a factory method for plugins. JDBC drivers, java.nio.file.spi.FileSystemProvider and logging backends are discovered at runtime and created through it, which is how the JDK stays open for extension.
    • Factories are good startup checkpoints. Production systems create critical clients during startup (or readiness checks) so a bad config fails the deployment and the rollout stops automatically.
    • Factory Method vs DI. Containers made many hand-written factories unnecessary; what remains are factories for runtime choices (per merchant, per request), which the container can't make at wiring time. A common modern shape: the container injects a factory, and the factory makes per-key objects.

    War story: the factory that read the wrong environment

    A grocery platform's payments team had a GatewayFactory that picked sandbox or live by reading an environment variable. A new staging cluster was created by copying production manifests, and the variable said prod. Staging test orders hit the live card network for a morning, charging test cards that, luckily, were declined. The fix: the factory refused live gateways unless both the environment and a signed deployment flag agreed, and it logged its choice at startup, where an alert checked it. Lesson: a factory that selects something dangerous should validate its inputs, not just obey them.

    18. Interview Corner¶

    1. What problem does Factory Method solve? It decouples callers from concrete classes, so the created type can vary.
    2. What are the roles? Product, concrete product, creator, concrete creator.
    3. Give a JDK example of a static factory. List.of, Integer.valueOf, LocalDate.of.
    4. Static factory vs constructor? Static factories have names, can cache, can return subtypes; constructors can't.
    5. Is a simple factory a GoF pattern? No; it's a common idiom. Factory Method uses subclasses.
    1. Factory Method vs Abstract Factory? Factory Method creates one product via a method; Abstract Factory creates families of related products via an object.
    2. How does Factory Method relate to Template Method? The factory method is often one step of a template method.
    3. How do you keep a parameterised factory extensible? Use a registry (Map<Key, Supplier<T>>) or ServiceLoader.
    4. Why avoid default in an enum switch factory? It hides missing cases from the compiler.
    5. When would you inject a Supplier<T>? When code needs new instances on demand and tests need control (IDs, buffers).
    1. Design a payment gateway factory for 5,000 merchants across regions. Config-driven registry, per-merchant cached clients, environment guards, startup warm-up of top merchants, metrics on creation failures.
    2. Factories vs DI containers: what still needs a factory? Runtime choices by key or request, which the container can't know at wiring time.
    3. How would you let other teams add exporters without touching your code? ServiceLoader or a registration API with a stable product interface and contract tests.
    4. computeIfAbsent with slow creation under load: what happens? Threads for the same bin block; move slow I/O out or use futures as values.
    5. Now 10x traffic, and clients are created per request. What do you change? Cache per key, add pooling, and pre-create hot clients.

    20. Quick Revision Card¶

    Remember in 30 seconds

    • Intent: let something other than the caller decide which class to create.
    • Classic: abstract createX() in a creator, overridden by subclasses.
    • Everyday Java: static factories (of, valueOf), enum switch, registries, Supplier<T>.
    • Validate and fail clearly in the factory; cache expensive products per key.
    • Not for one stable implementation; not for families (Abstract Factory) or many options (Builder).
